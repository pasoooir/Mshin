# قرارداد فنی کیفیت، پایداری و تجربهٔ بازی Mshin در Godot 4.3

این سند قرارداد اجرایی پروژه است. قابلیت فقط وقتی تکمیل محسوب می‌شود که در بازی قابل استفاده باشد، تست خودکار متناسب داشته باشد و محدودیت‌های پلتفرم هدف را پاس کند.

## 1) پلتفرم و نسخهٔ موتور
- نسخهٔ مبنا Godot 4.3 و GDScript استاندارد است؛ APIهای نسخه‌های جدیدتر بدون بررسی سازگاری وارد نشوند.
- خروجی وب باید با GL Compatibility کار کند. خروجی Android جداگانه تست شود.
- هیچ تغییر رندرر یا تنظیم گرافیکی صرفاً بر اساس ظاهر Editor پذیرفته نیست؛ Web و Android جداگانه Import، اجرا و Export شوند.
- اولویت موبایل: landscape، fullscreen در صورت اجازهٔ مرورگر/سیستم، safe-area، لمس چندانگشتی و رابط خوانا.

## 2) معماری: اول قابلیت‌های داخلی Godot
از APIهای داخلی پایدار استفاده کن و dependency اضافه نکن مگر نیاز فنی مستند و تست سازگاری داشته باشد:
- UI و تعامل: Control، Container، Theme/StyleBox، Button، TextureRect، signals، InputEventScreenTouch و InputEventScreenDrag.
- انیمیشن: AnimationPlayer برای توالی‌های قابل‌ویرایش؛ Tween برای گذارهای کوتاه.
- داده و دارایی: Resource/ResourceLoader، PackedScene، GLTFDocument/GLTFState برای GLB/GLTF محلی.
- رندر و مقیاس: MultiMeshInstance3D برای تکرار انبوه؛ LOD/visibility ranges، culling و batching فقط با اندازه‌گیری.
- منطق: typed GDScript و typed collections، سیگنال‌های مشخص، کلاس‌های کوچک با مسئولیت واحد و state machine صریح.
- زمان‌بندی تولید: finish timestamp مرجع حقیقت باشد؛ شمارش UI از اختلاف زمان فعلی با timestamp محاسبه شود، نه کم‌کردن دستی عدد در هر فریم.
- Save/Load: دادهٔ نسخه‌دار، اعتبارسنجی و migration سازگار با ذخیره‌های قبلی.

## 3) رابط تولید — الزام غیرقابل‌مذاکره
- پنل صف مطابق مرجع کاربر: قاب آبی/فیروزه‌ای، عنوان واضح، کارت‌های گرد، خانه‌های خالی با + بزرگ و خانه‌های پر با تصویر واقعی محصول، تعداد و تایمر خوانا.
- حداقل شش خانه قابل‌مشاهده؛ ظرفیت خریداری‌نشده باید واضح و غیرقابل‌استفاده قفل باشد.
- لمس/کلیک محصول معتبر باید در همان اقدام آن را در اولین slot آزاد همان ساختمان ثبت کند؛ مرحلهٔ دوم، drag اجباری یا TAP TO START ممنوع.
- تصویر، شناسه، تعداد، زمان شروع و پایان هر خانه متعلق به همان سفارش باشد؛ سفارش‌ها بین کارخانه/فروشگاه/خانه نشت نکنند.
- تایمر به‌صورت ثانیهٔ صحیح نزولی از timestamp واقعی محاسبه شود؛ پس از reload/resume صحیح بماند؛ در صفر Ready شود و منفی نمایش داده نشود.
- پایان تایمر به‌تنهایی کالا را به انبار منتقل نکند؛ فقط Collect موفق با ظرفیت کافی خروجی را اضافه کند. انبار پر نباید خروجی آماده را حذف کند.
- پیش‌نیاز ناموجود، صف پر، ساختمان نامعتبر/غیرفعال، لمس تکراری، لمس سریع چندمحصولی و تعویض ساختمان باید رفتار مشخص و بدون مصرف/ثبت تکراری داشته باشند.
- انیمیشن/صدا/هایلایت منبع حقیقت اقتصاد نیستند؛ ProductionManager و StorageManager مرجع یگانهٔ داده‌اند.

## 4) کیفیت بصری و کارایی شهر سه‌بعدی
- هدف هنری: محلهٔ زنده و خوانا با مقیاس واقعی، ساختمان‌های دارای silhouette و هویت عملکردی، مصالح PBR، پنجره/در/سقف/تابلو، خیابان آسفالتی با خط‌کشی و جدول، فضای سبز متنوع و نور و سایهٔ کنترل‌شده؛ نه شهر مکعبی یا زمین تخت تک‌رنگ.
- واحد جهان 1 متر؛ footprint و ارتفاع هر خانوادهٔ ساختمان با مشخصات کاتالوگ سازگار باشد.
- مدل‌های GLB/GLTF محلی با provenance/license ثبت‌شده؛ placeholder فقط برای توسعه و با برچسب روشن، نه تحویل نهایی.
- draw-call، حافظه، تعداد material، وضوح texture، shadow casters و frame time اندازه‌گیری شود. FPS بدون پروفایل روی دستگاه واقعی ادعا نشود.
- transparency، post-processing و سایه‌های پرهزینه با احتیاط؛ برای اشیای تکراری instancing و برای فاصلهٔ دور LOD بررسی شود.
- گرافیک تطبیقی: کیفیت پایه برای دستگاه ضعیف و گزینه‌های افزایشی برای دستگاه قوی؛ افت فریم نباید ورودی و منطق بازی را مختل کند.

## 5) استاندارد کدنویسی و کنترل خطا
- از node path شکننده، get_node بدون بررسی در مرزهای پویا، اتصال تکراری signal، global state پنهان و منطق کپی‌شده اجتناب کن.
- هر signal connection باید مالک/چرخهٔ عمر روشن داشته باشد و پس از آزادسازی یا تعویض پنل stale نماند.
- عملیات اقتصاد اتمیک باشد: validate/reserve سپس commit؛ در شکست هیچ ماده/پول/slot نیمه‌مصرف نشود.
- ورودی کاربر idempotent یا در برابر double-tap محافظت‌شده باشد.
- خطاها پیام قابل‌فهم داشته باشند؛ نتیجهٔ تست جعلی یا catch خاموش خطا ممنوع.
- هر dependency ثالث باید نسخهٔ ثابت، مجوز، سازگاری با Godot 4.3 و Web/Android، حجم خروجی و دلیل انتخاب داشته باشد. اگر API داخلی کافی است، کتابخانهٔ ثالث اضافه نکن.

## 6) گیت‌های تست اجباری
1. Static validation و بررسی منابع/دارایی‌ها.
2. Import و parse کامل پروژه با Godot 4.3 headless.
3. Headless startup smoke.
4. Gameplay integration test.
5. تست مسیر واقعی signal UI: اتصال واقعی، ورودی touch/mouse و ثبت فقط یک سفارش.
6. تست اقتصاد: پیش‌نیاز ناکافی، مصرف اتمیک، صف پر، ظرفیت قفل، انبار پر، collect، save/load و resume timer.
7. تست پنل: شش slot، هویت محصول هر slot، تایمر ثانیه‌ای، رسیدن به صفر، تعویض ساختمان بدون آلودگی UI.
8. City visual geometry smoke و بررسی ساختار صحنه.
9. Web export و اجرای Chromium در viewport موبایل و دسکتاپ.
10. Android Debug APK export و بررسی امضا/package.
11. تست دستی حداقل یک گوشی واقعی برای لمس، landscape، safe-area، حرارت و کیفیت بصری؛ CI یا شبیه‌ساز جای گوشی واقعی نیست.

## 7) Definition of Done
- تمام workflowهای مرتبط روی آخرین SHA موفق باشند؛ نه SHA قبلی.
- regression شناخته‌شده یا تست skip‌شده برای رفتار اصلی باقی نماند.
- تستی که handler را مستقیم صدا می‌زند به‌تنهایی تست UI محسوب نمی‌شود؛ مسیر signal/event نیز باید پوشش داده شود.
- README/Tracker فقط بر اساس شواهد واقعی به‌روزرسانی شود.
- PR تا عبور گیت‌های خودکار merge نشود؛ تست دستگاه واقعی جداگانه گزارش شود.
- «بدون باگ» تضمین مطلق نیست؛ معیار، خطای بازتولیدپذیر صفر در سناریوهای پذیرش و پوشش رگرسیون برای باگ‌های رفع‌شده است.

## 8) روش اجرا
قبل از تغییر، علت ریشه‌ای را پیدا کن و تستی بنویس که قبلاً می‌توانست باگ را آشکار کند. تغییر کوچک، قابل‌بازبینی و سازگار با نسخهٔ موتور باشد. پس از تغییر، زنجیرهٔ مرتبط را روی commit نهایی اجرا کن، log شکست را بخوان، تا رفع علت ادامه بده و فقط نتیجهٔ اثبات‌شده را گزارش کن.
